# Hunyuan3D-2.1 pipeline on an RTX 2070 Mobile (8 GB, Turing sm_75)

Status 2026-10-20: emulated on RTX PRO 6000 (no real 2070M available). Full wolf run passed with
`--lowvram --vram-cap 7.0 --turing`. Output is bit-identical to the non-Turing run: same raw mesh (max vertex diff 0.0), same
textured.jpg and preview (MAE 0.0). No NaN or black textures.

## Requirements
- GPU: RTX 2070 Mobile 8 GB (any Turing+ 8 GB card). Not enough: 6 GB or less (shape DiT weights alone are 5.7 GiB fp16).
- Driver: **R580 or newer** (CUDA 13.x driver). CUDA 13 still supports sm_75; it dropped only Maxwell, Pascal and Volta.
  The custom_rasterizer is built with nvcc 13.4 and links cudart64_13; torch cu128 alone would only need R570.
  Check with `nvidia-smi`: the "CUDA Version" it shows must be 13.0 or higher.
- System RAM: 16 GB plus a **pagefile of at least 16 GB on an SSD** (system-managed is fine). Close browsers and games while it runs.
- Disk: about 40 GB (venv plus the HF cache: Hunyuan3D-2.1 shape, paint, DINOv2-giant, RealESRGAN).
- Windows 10/11, Python 3.12.

`pip install --no-deps --force-reinstall <whl>`. On the laptop, install this **wheel**. Don't rebuild there.

## Dtype / attention
- Every inference path is already **fp16**: shape `pipelines.py` dtype=float16, paint `multiview_utils.py` torch_dtype=float16
  plus DINO .to(float16), T2I float16. The only bf16 code is in training (`hunyuanpaintpbr/unet/model.py`, `flow_matching_sit.py`)
  and never runs here. The shape DiT uses `use_flash_attn=False` (SDPA).
- `--turing` (automatic when compute capability < 8.0) turns off flash and cuDNN SDPA (so SDPA uses mem-efficient, else math)
  and makes `torch.cuda.is_bf16_supported()` return False. Emulated result: bit-identical to the default run, no fp32 fallbacks needed.

## Changes in run_inbox.py
1. `--turing` flag plus auto-detect (in CAP_PREFIX, so it covers every GPU stage).
2. Low host RAM shape load (OFFLOAD_CHAIN): checkpoint opened with `torch.load(mmap=True)` and modules built directly in fp16
   (no fp32 copy). Shape peak working set went from **22.98 to 14.48 GiB**. About 5.7 GiB of that is mmap'd checkpoint pages that the OS
   can drop, so the real commit is about 9 GiB. The mesh is bit-identical.
3. PEAK lines now include `rss_peak` (psutil peak working set), stored in timings.json.
4. Paint OOM ladder: 6 views @512, then 4 @512, then 4 @384. It retries automatically when the log shows an OOM, and `paint_cfg` is
   recorded in timings.json. Not triggered at cap 7.0 (6 views fit), so **the ladder is untested**.
5. Fixed the stale `LAB` path (`E:/Github/anyCreature/creatures/harness/lab`). The old path broke the render step.

## Command
```
python run_inbox.py <animal> --seeds 0 --lowvram                 # phase 1: shape candidates + sheets
python run_inbox.py <animal> --seeds 0 --lowvram --pick h21_s0   # phase 2: paint, low-poly, rig, validate
```
On the laptop, `--turing` is automatic. Add `--vram-cap 7.0` to keep 1 GB free for the Windows desktop.

## Known limits
- The cap emulates torch allocations only. CUDA context plus driver adds about 0.3-0.5 GB, and the desktop or other apps can take 0.5-1 GB. With a cap of 7.0 plus
  a 0.5 GB context, the total is about 7.5 GB, which is tight but should fit. If paint OOMs, the ladder drops to 4 views (slightly blotchier texture on hidden sides).
- Laptop thermal throttling can stretch these times 1.5x.
- With 16 GB RAM and no pagefile, the shape load can fail. Keep the pagefile.
- 2mv multi-view shape path (side.png present) uses the same offload plus RAM fix but was not re-measured.
- T2I (HunyuanDiT) is not part of run_inbox. It was measured before at 4.0 GiB with fp16 and offload, so it fits.
